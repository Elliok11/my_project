# 本地大模型命令行助手


一个跑在**自己电脑上**的命令行 AI 助手：不联网、不调用云端 API，直接和本地部署的大模型对话；
再加上 YOLO 目标检测，它还能"看图说话"。

题目要求"完成本地大模型部署 → 搭建自己的智能体 → 将模型作为 provider，通过 API 接入自己的应用"。
本仓库记录了这个过程的**完整实现、踩坑记录与解决思路**，而不只是最后的代码。

**选型说明（为什么是 1.5B）**：本机是 11 年前的低功耗双核笔记本，CPU 是唯一可用的算力（两块显卡都不具备可用算力）。
在 CPU 上跑 7B 级模型体验无法接受，而 0.5B 又经常答非所问。实测 `qwen2.5:1.5b` 在本机可稳定达到约 **13 tokens/秒**，
是这个硬件配置下"跑得动"与"说得像人话"的平衡点。

## 快速开始（复现步骤）
:: 0. 进入项目目录
```
cd /d D:\desktop\my_project
```
:: 1. 安装 Ollama

::    下载 https://ollama.com/download/windows 并安装

:: 2. 拉取模型（约 1 GB）
```
ollama pull qwen2.5:1.5b
```
:: 3. 【关键】关闭 Vulkan，强制使用 CPU
::    不设这一步，本机会直接崩溃，详见"已知问题"
```
setx OLLAMA_VULKAN 0
```
:: 4. 启动服务（新开一个终端窗口，保持不关）
```
ollama serve
```
:: 5. 安装 Python 依赖
::    先装 CPU 版 PyTorch（约 200 MB），否则默认会下载 2.5 GB 的 CUDA 版本
```
py -3.11 -m pip install torch torchvision --index-url https://download.pytorch.org/whl/cpu
py -3.11 -m pip install -r requirements.txt
```

:: 6. 纯文字对话
```
python src/ai.py "用一句话解释什么是机器学习"
```
:: 7. 看图说话（首次运行会自动下载 6 MB 的 YOLO 预训练权重）

```
python src/ai.py -i data/samples/bus.jpg "这张图里有什么"
```

## 训练（在魔搭免费 GPU 上）

**为什么不在这台笔记本上训练**：本机是双核 CPU、没有可用于训练的显卡（见"已知问题"）。
训 50 轮 coco128 在本机需要数小时，而在免费 GPU 上约 5 分钟。

**为什么选魔搭**：本机**无法访问 Google Colab**（实测超时），网上大多数 YOLO 教程需要跳过。
魔搭（ModelScope）提供免费 GPU 额度，环境基于 PAI-DSW，预装 CUDA 与 PyTorch。

**步骤**：

1. 在 [modelscope.cn](https://www.modelscope.cn/) 注册，进入「我的 Notebook」
2. 新建 Notebook，选择**带 GPU 的环境**，启动
3. 在 JupyterLab 的代码格里执行：

```python
!pip install ultralytics -q
!git clone https://github.com/Elliok11/my_project.git && cd my_project
!python train/train_yolo.py --data coco128.yaml --epochs 50 --batch 16 --device 0
```

4. 训练完成后下载 `runs/train/weights/best.pt`，放进本机 `weights/` 目录
5. 用自己训练的权重推理：

```cmd
python src/ai.py -i data/samples/bus.jpg "这张图里有什么" --weights weights/best.pt
```

**训练参数的选择理由**（题目要求"参数自己决定"，这里给出依据）：

| 参数 | 取值 | 理由 |
|---|---|---|
| 基础模型 | `yolov8n` | 最小最快的版本，本机 CPU 推理能跑得动（约 3.3 秒/张） |
| `epochs` | 50 | 小数据集下足够收敛；过少欠拟合，过多过拟合 |
| `imgsz` | 640 | YOLO 的标准输入尺寸，精度与速度的通用平衡点 |
| `batch` | 16 | 24G 显存下宽裕；若改在本机 CPU 训练则必须调小 |
| `device` | 0 | 使用第 0 号 GPU；本机 CPU 训练填 `cpu` |

> ⚠️ 魔搭的免费额度按使用时长消耗，**训练完请及时停止实例**，并把权重下载到本地。

## 创意作品：相册智能分类工具（题目五）

**它解决什么问题**：照片越攒越多，翻找全靠手划。这个工具用 YOLO 自动"看懂"每张照片里的物体，
按人类翻相册的习惯分类归档，并生成一份可检索的图文报告。

### 分类标准是怎么定的

1. 先查出模型能识别的**全部类别**（本模型为 COCO 的 80 类）
2. 再按"翻相册的习惯"把它们归成 10 组：
   人像 / 宠物动物 / 美食餐具 / 交通工具 / 电子设备 / 家具室内 / 户外街道 / 运动娱乐 / 随身物品 / 玩具其他
3. 用 128 张真实照片跑 `--dry-run`，**用实际分布验证方案是否合理**

> 为什么先做第 1 步？如果凭空定分类（比如"风景""美食""人像"），
> 很可能定出模型根本认不出的类别（模型只认"物体"，不认"场景"），工具就会大面积失效。

### 遇到的设计问题：一张图有多种物体，归哪一类？

实测发现「随身物品」有 **0 张** —— 因为只要照片里有人，就一律被归到「人像」，
"一个人背着背包"的照片里，背包就"消失"了。于是实现了两种策略并做对照：

| 策略 | 规则 | 128 张实测：人像占比 | 随身物品 |
|---|---|---|---|
| `priority` | 按固定优先级（人像最优先） | 42.2% | **0 张** |
| **`count`（默认）** | 哪类物体数量最多就归哪类 | 35.2% | 3 张 |

最终选择 `count`，因为它更贴近"**这张照片主要拍了什么**"。

### 用法


:: 对比两种策略的分布（不复制任何文件）
```
python src/organizer.py -i data/album --dry-run
```
:: 正式分类
```
python src/organizer.py -i data/album -o output/album_sorted --strategy count
```

| 分类 | 数量 | 占比 |

| 人像 | 45 | 35.2% |
| 宠物动物 | 20 | 15.6% |
| 美食餐具 | 16 | 12.5% |
| 交通工具 | 14 | 10.9% |
| 电子设备 | 10 | 7.8% |
| 家具室内 | 10 | 7.8% |
| 玩具其他 | 4 | 3.1% |
| 随身物品 | 3 | 2.3% |
| 户外街道 | 2 | 1.6% |
| 运动娱乐 | 2 | 1.6% |
| 未识别 | 2 | 1.6% |

### 用个人相册实测（52 张真实照片）

用 COCO 数据集测出的漂亮数字**不能代表真实使用场景**，所以又拿 **52 张个人相册照片**（以微信收到的图片为主）测了一遍：

| 参数 | 未识别 | 人像 | 电子设备 | 家具室内 |
|---|---|---|---|---|
| `imgsz=320, conf=0.35` | **21 张（40.4%）** | 7 | 3 | 2 |
| **`imgsz=640, conf=0.25`（现默认）** | **14 张（26.9%）** | 11 | 5 | 3 |

**两个结论**：

1. **未识别率从 1.6% 涨到 40.4%** —— 印证了"不能拿 COCO 的数字到处宣传"。
   个人相册里大量是网传图、截图、课件照片，没有模型能识别的物体
2. **参数调优确实有效**：推理尺寸从 320 提回 640、阈值从 0.35 放宽到 0.25 后，
   未识别率降到 **26.9%**，找回 7 张


### 剩余未识别照片的分析

14 张未识别的照片**全部是微信传输的图片**，且 **EXIF 元数据被微信剥离**
（实测 0/14 带相机 EXIF），因此"用 EXIF 区分拍照 / 截图"的思路在这类图片上无效。

### 升级：两级流水线（检测 + 分类兜底）⭐ 项目最核心的设计决策

上面测出的 26.9% 未识别**不是"参数没调好"，而是任务类型不匹配**：

| | 目标检测（detect） | 图像分类（classify） |
|---|---|---|
| 回答什么 | 物体**在哪**、是什么 | **整张图**属于哪一类 |
| 标注成本 | 必须逐个画框 | 只要按类别放进文件夹（**零标注**） |
| 适合截图/文档/风景吗 | ❌ 这些图**没有"物体位置"可框** | ✅ 正好 |

于是把工具改成两级流水线：

```
照片 → 【第一级】YOLO 物体检测
            ├── 检测到物体 → 按物体归类（人像 / 宠物动物 / 美食餐具……）
            └── 没检测到   → 【第二级】分类模型判断整图类型（截图/文档/风景/表情包）
```

**第二级的分类模型是自己采集标注数据训练的**：

| 项目 | 内容 |
|---|---|
| 数据 | 自己收集 **1027 张**（5 类），按 8:2 **独立划分** |
| 模型 | `yolov8n-cls`（ImageNet 1000 类预训练 → 改为 5 类） |
| 训练 | 魔搭免费 GPU，`epochs=50, imgsz=224, batch=32` |
| **独立验证集 Top-1** | **94.6%**（204 张验证集，与训练集不重叠） |
| 推理速度 | **14.1 ms/张**（比检测快约 230 倍，几乎不增加开销） |

**A/B 对照实验结果**（同一批 52 张个人相册）：

| | 只用检测（旧） | 检测 + 分类兜底（新） |
|---|---|---|
| YOLO 检测判定 | 38 张 | 38 张 |
| 分类兜底判定 | 0 张 | **14 张** |
| **未识别** | **14 张（26.9%）** | **0 张（0%）** ✅ |

那 14 张原来"没人认识"的照片，现在被归类为：**风景 9 张、美食餐具 3 张、文档 1 张、表情包 1 张**。

### 一些小反思（这里真不是用AI写的）
1. 收集数据的时候，手机截图其实是一个重灾区。因为截图理论上是能够包含所有东西，表情包，风景，视频通话挂小屏也能被分类进人像。问过AI，说这个就是通过数量与多样性让ai抓住截图的本质——UI或者是手机操作界面来判断它是个截图
2. 截图和表情包其实是很大程度上受到限制的，我只收集了几个群友的表情包，截图只用了包括我在内的四个人提供的素材，可能会让AI陷入一种另类的“信息茧房”，就是可能会不认得其他款式的截图或者表情包，这个我后面会尝试验证我的猜想。
3. 关于它试图的架构问题：先识别“按物体检测”，没检测到物体再调用我训练的几个分类。其实它第一级识别的时候已经识别了比较大一部分的了，还有可能“截流”掉一些本来属于“风景”“截图”的图片，我在想其实能不能直接去掉第一级识别，或者把这两级合并（于是我叫AI这样做了，就进行了一波改动）

## 已知问题与解决方案

### 问题 1：`ollama run` 崩溃，报 `0xc0000005`

**现象**：模型下载成功，但一运行就报
`500 Internal Server Error: llama-server process has terminated: exit status 0xc0000005`

**定位过程**（这是本项目最耗时的部分，完整记录见 `logs/2026-10-09.md`）：

1. 排除模型损坏 —— sha256 校验通过，重复下载无效
2. 排除"虚拟机缺 AVX 指令集" —— `systeminfo` 确认是物理机，CPU 为 Broadwell 架构，支持 AVX2
3. 排除 VC++ 运行库缺失 —— `vcruntime140.dll` 已是 14.44 版本
4. **读 Windows 事件日志（事件 ID 1000）**，拿到崩溃模块：
   ```
   错误应用程序名称: llama-server.exe
   错误模块名称:     vulkan-1.dll
   异常代码:         0xc0000005
   ```
5. **读 Ollama 引擎日志**，发现它在做一件不该做的事：
   ```
   load_tensors: offloaded 19/29 layers to GPU
   load_tensors:      Vulkan0 model buffer size =  605.40 MiB
   ```
6. **在系统 DriverStore 中找到这块"显卡"的真身**：`amd-vulkan64.json` → `amdvlk64.dll`（2020 年的实现）

**根因**：Ollama 默认把本机的 **AMD R7 M260**（2013 年、2 GB 显存、驱动停留在 2020 年）识别为可用加速卡，
把 19/29 层模型权重搬上去，搬运过程中驱动崩溃，整个推理引擎随之挂掉。**与模型、CPU、内存、Ollama 版本均无关。**

**解决方案**：设置环境变量，禁止 Ollama 使用 Vulkan：

```cmd
setx OLLAMA_VULKAN 0
```

**验证方法**：先做 6 组对照实验确认（`OLLAMA_VULKAN=0`、`OLLAMA_VULKAN=false`、`OLLAMA_LLM_LIBRARY=cpu` 三组均成功；
`GGML_VK_VISIBLE_DEVICES`、`VK_DRIVER_FILES` 两组无效），再固定使用 `OLLAMA_VULKAN=0`。

## 实测性能

### 大模型（qwen2.5:1.5b）

| 指标 | 数值 |
|---|---|
| 模型加载时间 | 约 5 秒（首次） |
| 生成速度 | 约 12.9 tokens/秒 |
| 运行方式 | 纯 CPU（无 GPU 卸载） |
| 内存占用 | 约 1.4 GB（模型 934 MB + 运行时缓冲） |

### YOLO（yolov8n，COCO 80 类预训练权重）

| 指标 | 数值 |
|---|---|
| 单张图片推理 | 约 3.3 秒 |
| 权重文件大小 | 6.25 MB |
| 运行方式 | 纯 CPU |
| 实测样例 | `bus.jpg` 检出公交车 + 3 名行人 + 停车标志 |

### 训练（魔搭免费 GPU，NVIDIA A10）

| 项目 | 数值 |
|---|---|
| 数据集 | coco128（128 张，COCO 子集） |
| 基础模型 | `yolov8n.pt`（迁移学习，非从零训练） |
| 训练参数 | `epochs=50, imgsz=640, batch=16, device=0` |
| 训练耗时 | 约 2 分钟（不含 6 分钟的数据下载） |
| **mAP50** | **0.852** |
| mAP50-95 | 0.675 |
| precision / recall | 0.869 / 0.779 |
| 产物 | `runs/detect/train/weights/best.pt`（6.24 MB） |

**一个观察**：在本机示例图 `zidane.jpg` 上，小目标 `tie`（领带）的置信度由官方权重的 0.29 提升到 0.78。
这说明用自己数据微调可以改善特定目标——但**单张图的观察不足以作为普遍结论**，需要更多验证才能下判断。

> ⚠️ **上面这个 mAP50 = 0.852 不能当作泛化性能** ：
> 打开官方 `coco128.yaml` 可以看到，**`train` 和 `val` 指向同一批 128 张图**：
>
> ```yaml
> train: images/train2017   # 128 images
> val:   images/train2017   # 128 images
> ```
>
> 而且这 128 张图来自 COCO train2017，官方预训练权重本来就见过它们。
> 也就是说，这是**"在训练过的数据上自我评估"**得到的分数，它只能证明
> **训练流程已经跑通**，**不能说明模型对新图片的泛化能力**。
>
> 仍然选择 coco128 的理由：它的定位是**用最小代价跑通「训练 → 推理 → 接入应用」的完整链路**，
> 而不是追求精度。若要真实评估模型能力，必须使用与训练集完全独立的验证集。
