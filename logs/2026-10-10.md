## 今天的思路

### 1. 为什么 CLI 要直接调 HTTP API，而不是调用 `ollama run` 命令？

两种做法都能"跟模型说话"：

| 做法 | 优点 | 缺点 |
|---|---|---|
| 用 Python 调 `ollama run` 命令 | 简单 | 拿到的是一堆终端输出，要自己解析；换模型服务就要重写 |
| **直接调 HTTP API** | 返回结构化 JSON，可控制流式输出、system 提示词 | 需要多写几行 HTTP 代码 |

选择 **HTTP API**：因为题目要求"通过 API 的形式接入到自己的应用中"。
而且一旦走 API，本地模型和云端模型（OpenAI 格式）在代码层面差异极小，
以后换 provider 只需要改一个 URL —— 这是把本地部署的价值真正用起来了。

### 2. 代码结构上的取舍（做减法）

题目提到"AI 会不断把事情变繁琐，而你需要为事情做减法"。因此明确**不做**：

- 配置文件（toml/yaml）—— 两个参数不需要
- 插件系统、抽象基类、多 provider 适配层 —— 只有一个 provider
- 异步、concurrent.futures —— 单次提问不需要
- 彩色日志框架 —— `print` 够用

只做**能演示、能看懂**的部分：`argparse` 解析参数 → `requests.post` 调 API → 打印结果。

### 3. 保留的扩展点（为后面几天留位置）

- `-i/--image` 参数：为 YOLO 接入预留（Day 3 实现）
- 多轮对话：需要把 `/api/generate` 换成 `/api/chat`（payload 从 `prompt` 变成 `messages` 数组）
- 流式输出已经实现：这是演示效果最好的一步

## 遇到的问题

### 问题 1：`src/ai.py` 被理解成了文件名 `srcai.py`

第一次理解错了路径写法：`src/ai.py` 中 `src` 是**文件夹**，`ai.py` 是**文件**。
结果建了一个名叫 `srcai.py` 的文件，另外建了一个空文件夹。

**解决**：统一整理为 `src/ai.py`，删除空文件夹。
**教训**：路径中 `/` 是目录分隔符，不是一个字符。

### 问题 2：`ollama run` 依赖后台服务

CLI 是客户端，必须有 `ollama serve` 在后台运行。
如果没启动，程序会报连接错误。已在代码中捕获 `ConnectionError` 并给出中文提示。

## 下午：YOLO 部分开工（推理已跑通）

### 环境检查的意外收获

本来准备安装 YOLO 依赖，结果发现**机器上早就装好了**，而且 PyTorch 恰好是 CPU 版本：

```
torch 2.14.1+cpu       ← 已是 CPU 版，省下 2.5 GB 下载
torchvision 0.29.1
ultralytics 8.4.170
CUDA 可用: False       ← 符合预期
```

**经验**：动手装之前先查一遍已装了什么（`py -3.11 -c "import torch; print(torch.__version__)"`），
能省掉大量无谓的等待和磁盘占用。

### 写了什么

`src/detector.py` —— 只负责"看"的模块：

- `detect(图片路径)`：返回 `[{"label": ..., "confidence": ..., "box": [...]}]`
- `format_for_llm(检测结果)`：把结果汇总成一句给大模型的提示词
- 用全局字典缓存模型对象，避免每次调用都重新读盘（每次省几秒）

### 用官方预训练权重先跑通

没有独显，所以**先用官方 `yolov8n.pt`（6 MB，能识别 COCO 80 类）跑通推理链路**，
训练自己的权重留到下一步。实测：

```
bus.jpg    → 公交车(0.873) + 行人×3 + 停车标志(0.255)   约 3.3 秒
zidane.jpg → 两个人(0.836/0.819) + 领带(0.291)          约 3.4 秒
```

### 接入 CLI：YOLO 负责"看"，大模型负责"说"

在 `src/ai.py` 中加了 `-i/--image` 参数，流程是：

1. YOLO 检测图片 → 结构化结果（类别 + 置信度）
2. 结果写成一段文字塞进给大模型的 prompt
3. 大模型用自然语言描述这个场景

实测输出：

```
[YOLO] 检测到 4 个目标: bus(0.873), person(0.866), person(0.853), person(0.825)
[大模型] 这是一张包含一辆公交车和三个行人场景的图片。
```

### 一次"做减法"式的优化

第一版把**每个目标的置信度**都贴给大模型，结果 1.5B 的小模型开始念数字：

> "…行人中，有两人（置信度0.866和0.853）和一人（置信度0.261）的出现…"

两个改进：

1. **`format_for_llm` 只给"类别 × 数量"** —— 信息更紧凑，弱模型不容易被一串小数带跑偏
2. **置信度阈值从 0.25 提到 0.35** —— 过滤掉 `stop sign(0.255)`、`tie(0.291)` 这类噪声检测

改进后：

> "这是一张包含一辆公交车和三个行人场景的图片。"

**沉淀出的思路**：模型能力有限时，**把确定性的活儿交给代码，把生成性的活儿交给模型**。
分类计数是确定性的，用 Python 做；组织语言是生成性的，交给大模型。

### 发现的一个限制

1.5B 模型**有时不遵守指令**（即使明确写了"不要出现数字"，它偶尔还是会念置信度）。
这是小模型的固有限制，不是代码 bug。**记录它，而不是假装没有。**
