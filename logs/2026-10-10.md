## 今天的思路

### 1. 为什么 CLI 要直接调 HTTP API，而不是调用 `ollama run` 命令？

两种做法都能"跟模型说话"：

| 做法 | 优点 | 缺点 |
|---|---|---|
| 用 Python 调 `ollama run` 命令 | 简单 | 拿到的是一堆终端输出，要自己解析；换模型服务就要重写 |
| **直接调 HTTP API** | 返回结构化 JSON，可控制流式输出、system 提示词 | 需要多写几行 HTTP 代码 |

选择 **HTTP API**：因为题目要求"通过 API 的形式接入到自己的应用中"。
而且一旦走 API，本地模型和云端模型（OpenAI 格式）在代码层面差异极小，
以后换 provider 只需要改一个 URL —— 这是把本地部署的价值真正用起来了。

### 2. 代码结构上的取舍



- 配置文件（toml/yaml）—— 两个参数不需要
- 插件系统、抽象基类、多 provider 适配层 —— 只有一个 provider
- 异步、concurrent.futures —— 单次提问不需要
- 彩色日志框架 —— `print` 够用

只做**能演示、能看懂**的部分：`argparse` 解析参数 → `requests.post` 调 API → 打印结果。

### 3. 保留的扩展点（为后面几天留位置）

- `-i/--image` 参数：为 YOLO 接入预留（Day 3 实现）
- 多轮对话：需要把 `/api/generate` 换成 `/api/chat`（payload 从 `prompt` 变成 `messages` 数组）
- 流式输出已经实现：这是演示效果最好的一步

## 下午：YOLO 部分开工（推理已跑通）

### 环境检查的意外收获

本来准备安装 YOLO 依赖，结果发现**机器上早就装好了**，而且 PyTorch 恰好是 CPU 版本：

```
torch 2.14.1+cpu       ← 已是 CPU 版，省下 2.5 GB 下载
torchvision 0.29.1
ultralytics 8.4.170
CUDA 可用: False       ← 符合预期
```

**经验**：动手装之前先查一遍已装了什么（`py -3.11 -c "import torch; print(torch.__version__)"`），
能省掉大量无谓的等待和磁盘占用。

### 写了什么

`src/detector.py` —— 只负责"看"的模块：

- `detect(图片路径)`：返回 `[{"label": ..., "confidence": ..., "box": [...]}]`
- `format_for_llm(检测结果)`：把结果汇总成一句给大模型的提示词
- 用全局字典缓存模型对象，避免每次调用都重新读盘（每次省几秒）

### 用官方预训练权重先跑通

没有独显，所以**先用官方 `yolov8n.pt`（6 MB，能识别 COCO 80 类）跑通推理链路**，
训练自己的权重留到下一步。实测：

```
bus.jpg    → 公交车(0.873) + 行人×3 + 停车标志(0.255)   约 3.3 秒
zidane.jpg → 两个人(0.836/0.819) + 领带(0.291)          约 3.4 秒
```

### 接入 CLI：YOLO 负责"看"，大模型负责"说"

在 `src/ai.py` 中加了 `-i/--image` 参数，流程是：

1. YOLO 检测图片 → 结构化结果（类别 + 置信度）
2. 结果写成一段文字塞进给大模型的 prompt
3. 大模型用自然语言描述这个场景

实测输出：

```
[YOLO] 检测到 4 个目标: bus(0.873), person(0.866), person(0.853), person(0.825)
[大模型] 这是一张包含一辆公交车和三个行人场景的图片。
```

### 一次"做减法"式的优化

第一版把**每个目标的置信度**都贴给大模型，结果 1.5B 的小模型开始念数字：

> "…行人中，有两人（置信度0.866和0.853）和一人（置信度0.261）的出现…"

两个改进：

1. **`format_for_llm` 只给"类别 × 数量"** —— 信息更紧凑，弱模型不容易被一串小数带跑偏
2. **置信度阈值从 0.25 提到 0.35** —— 过滤掉 `stop sign(0.255)`、`tie(0.291)` 这类噪声检测

改进后：

> "这是一张包含一辆公交车和三个行人场景的图片。"

**沉淀出的思路**：模型能力有限时，**把确定性的活儿交给代码，把生成性的活儿交给模型**。
分类计数是确定性的，用 Python 做；组织语言是生成性的，交给大模型。

### 发现的一个限制

1.5B 模型**有时不遵守指令**（即使明确写了"不要出现数字"，它偶尔还是会念置信度）。
这是小模型的固有限制，不是代码 bug。**记录它，而不是假装没有。**

### 验证：用自己训练的权重跑通端到端

```
[YOLO] 检测到 4 个目标：person(0.916), person(0.876), person(0.851), bus(0.599)
[大模型] 这张图里可能是一张公交车站的画面，有三个人在候车。
```

一个小观察：小目标 `tie`（领带）的置信度从官方权重的 0.29 提升到 0.78。
**但这是单张图的观察，不足以作为普遍结论** —— 记录现象，不下过度结论。

### 重要：这个 mAP50 不能当泛化性能看

拉了官方 `coco128.yaml` 核对，发现：

```yaml
train: images/train2017   # 128 images
val:   images/train2017   # 128 images    ← 与训练集是同一批图
```

再加上这 128 张图来自 COCO train2017，而官方预训练权重本来就见过这些图。

**结论**：`mAP50 = 0.852` 是"在训练过的数据上自我评估"的分数，
只能证明**训练流程跑通了**，**不能说明泛化能力**。
若要做真实评估，必须换用与训练集完全独立的验证集。

**这条教训值得记住**：看到一个漂亮的指标，先去确认"它是怎么算出来的"，
而不是直接拿它当结论。面试时被追问"你的 mAP 可信吗"，答案就在这里。

## 创意作品：相册智能分类工具（题目五）

### 为什么做这个

照片越攒越多，翻找全靠手划。用 YOLO 自动"看懂"照片里有什么，按翻相册的习惯自动归档，
并生成一份可检索的图文报告。

### 关键做法：先摸清模型能力，再定分类标准

**没有凭想象定分类**（那样会定出模型根本认不出的类别 —— 模型只认"物体"，不认"场景"），而是：

1. 先列出模型能识别的全部类别 —— 80 个 COCO 类别
2. 按"翻相册的习惯"把它们归成 10 组
3. 用 128 张真实照片跑 `--dry-run`，**用实际分布验证方案是否合理**

### 遇到的设计问题：一张图检测到多种物体，归哪一类？

第一次跑完发现「随身物品」有 **0 张** —— 因为只要照片里有人，就一律归到「人像」，
"一个人背着背包"的照片里，背包就"消失"了。

于是实现了两种策略并做对照实验：

| 策略 | 规则 | 人像占比 | 随身物品 |
|---|---|---|---|
| `priority` | 按固定优先级（人像最优先） | 42.2% | 0 张 |
| **`count`** | 哪类物体数量最多就归哪类 | 35.2% | 3 张 |

最终选 `count`，理由是它更贴近"**这张照片主要拍了什么**"。

### 实测结果

128 张真实照片，纯 CPU，`imgsz=320`，约 2 分钟跑完：

```
人像 45  宠物动物 20  美食餐具 16  交通工具 14  电子设备 10
家具室内 10  玩具其他 4  随身物品 3  户外街道 2  运动娱乐 2  未识别 2
```

### 一个工程上的小优化

`imgsz` 从 640 降到 **320**：本工具只需要判断"画面里**有没有**这个物体"，
不需要精确的框位置，尺寸减半可以显著提速。

### 诚实说明的局限

- 本工具按"画面里的物体"分类，**不做场景理解**；纯风景照、截图、文档会落入「未识别」
- 在 COCO 这类物体密集的照片上未识别率只有 **1.6%**，
  但换成**普通人的手机相册**（大量风景、截图、自拍），未识别率会明显升高
  —— **不能拿 1.6% 到处宣传**，这是使用前提
- 改进方向：引入场景分类模型（Places365）或图像描述模型；支持"一张图多标签归档"（硬链接避免占空间）

### 追加实验：用 52 张个人相册照片实测

**动机**：COCO 数据集上 1.6% 的未识别率太"漂亮"，不能代表真实场景，必须用自己的照片验证。

**结果**（52 张，以微信收到的图片为主）：

| 参数 | 未识别 | 人像 | 电子设备 | 家具室内 |
|---|---|---|---|---|
| `imgsz=320, conf=0.35` | **21 张（40.4%）** | 7 | 3 | 2 |
| `imgsz=640, conf=0.25` | **14 张（26.9%）** | 11 | 5 | 3 |

**这次实验推翻了我自己先前的一个决定**：
我最初把 `imgsz` 从 640 降到 320 来提速（理由：分类不需要精确框位置）。
它在 COCO 上没问题，但**换到个人相册后漏检明显增加**（40.4% vs 26.9%）。
**已把默认值改回 640。**

**教训**：在一个数据集上有效的优化，换个数据分布就可能失效。
参数必须在**目标场景**上验证，不能在方便的数据集上验证完就宣布成功。

**剩余 14 张未识别的排查**：
- 全部是微信传输的图片，且 **EXIF 被剥离**（实测 0/14 有 EXIF）
- → "用 EXIF 区分拍照/截图"的思路无效，此路已排除
