| 类别 | 数量 | 来源 |
|---|---|---|
| meme（表情包/聊天图） | 346 | 微信、QQ 收集 |
| food_cn（中式餐食） | 242 | 自己拍摄 |
| screenshot（截图） | 184 | 手机 + 电脑截图 |
| scenery（风景） | 135 | 自己拍摄 + 图库 |
| document（文档/试卷/笔记） | 120 | 自己拍摄 |

**收集时坚持的三条原则**（写在前面，避免返工）：

1. **多样性 > 数量**：每类都要有 3 个以上不同来源，避免模型学到"捷径"（比如把所有截图都拍成同一张壁纸，模型会学成"认壁纸"）
2. **避免近似重复**：同一场景连拍只留 2~3 张
3. **边界规则统一**：明确「屏幕渲染的画面 → screenshot」vs「被拍摄的纸质实物 → document」

## 二、⚠️ 卡住点 1：中文文件名导致训练崩溃（已解决）

### 现象

数据上传云端后，训练启动即崩溃：

```
UnicodeEncodeError: 'utf-8' codec can't encode characters in position 54-55:
surrogates not allowed
```

崩溃位置：`get_hash()` —— 计算数据集哈希时要把图片路径编码成 UTF-8。

### 排查

1. 先看崩溃位置：是在**算路径哈希**时报错，不是模型、不是数据格式
2. 检查发现问题根源：**1027 张里有 791 张是中文文件名**（主要是微信图片）
   ```
   document     81/120 张含中文名
   food_cn     242/242 张含中文名
   meme        289/346 张含中文名
   scenery     135/135 张含中文名
   screenshot   44/184 张含中文名
   ```

### 根因（完整链条）

```
Windows 文件名用 UTF-16 存储 → 中文名一直正常
        ↓
zip 打包时，中文名按本地编码（GBK）写入压缩包
        ↓
Linux 解压时按 UTF-8 解读这些字节 → 得到非法字节序列
        ↓
Python 用 surrogate（代理字符）表示这些坏字节
        ↓
训练时把路径编码回 UTF-8 算哈希 → 💥 surrogates not allowed
```

### 解决方案

修改 `src/prepare_cls_dataset.py`：

1. **所有图片统一重命名为纯 ASCII**：`<类别>_<序号>.jpg`（如 `screenshot_001.jpg`）
2. **生成 `manifest.csv`** 记录「原文件名 → 新文件名」对照，保留来源可追溯性
3. **类别文件夹名校验**：必须是纯英文/数字/下划线，否则直接报错退出
4. 顺带修掉一个隐患：不同子目录的同名文件会互相覆盖（现在自动加序号）

### 沉淀的教训

> **跨平台数据交换（尤其 Windows → Linux），文件名一律用 ASCII。**
> 中文可以写在文档和说明里，但不要出现在**被程序处理的文件路径**中。

### 关键发现：错误高度集中在一处

**11 张错误里有 5 张是「真实截图被判成 meme」** —— 最大的一处混淆。

### 原因：类别定义重叠

```
meme 类里收了大量「聊天截图」
        ↓
而聊天截图本身就是截图
        ↓
模型难以区分这两类的本质差别
```

**诚实记录**：我事先预判的是 `screenshot ↔ document` 会混淆，
**实际是 `screenshot ↔ meme`** —— 预判错了方向，但"截图类一定会出问题"这个判断是对的。

### 改进方向（未做，属未来工作）

1. 明确边界规则：「聊天界面截图 → 归 meme，其他 App 截图 → 归 screenshot」，并清理违规样本后重训
2. 或把 meme 拆成「聊天截图」「表情包」两类
3. 或接受 94.6%，并在 README 中如实说明这一局限

## 五、⚠️ 卡住点 2：GitHub 推送间歇性失败（已解决）

### 现象

```
fatal: unable to access 'https://github.com/...': Failed to connect to github.com:443
after 21116 ms: Could not connect to server
```

时好时坏，重试无效。

### 排查过程

1. `Test-NetConnection github.com -Port 443` → **TCP 层是通的** ✅
2. 用 `curl -v https://github.com` 看细节 → 卡在 **TLS 握手阶段**
   （`schannel: failed to receive handshake, need more data`）
   → 说明是**TCP 通、TLS 被干扰**，不是网络完全断开
3. 查看 hosts 文件，发现被某加速工具改过：
   ```
   127.0.0.1 github.com
   127.0.0.1 api.github.com
   127.0.0.1 raw.githubusercontent.com ...（一长串）
   ```
   该工具把 GitHub 域名指向本机，由本地中转；**但工具当前没在运行**（常见代理端口都无人监听）
4. 测试 SSH 通道：
   ```
   ssh -T -p 443 git@ssh.github.com
   → Hi Elliok11! You've successfully authenticated...
   ```
   **SSH 完全可用！**

### 根因

HTTPS 走 TLS 协议，从本机直连 GitHub 时 TLS 握手被干扰；
**SSH 不是 TLS 协议，不受影响**。

### 解决方案

把远程仓库地址从 HTTPS 换成 SSH（并走 443 端口，避免 22 端口被封）：

```bash
ssh-keyscan -p 443 ssh.github.com >> ~/.ssh/known_hosts
git remote set-url origin ssh://git@ssh.github.com:443/Elliok11/my_project.git
git push --force-with-lease origin main
```

### 沉淀的经验

> **推 GitHub 失败时，先分清是"完全不通"还是"TCP 通但 TLS 被干扰"。**
> 前者等网络恢复；后者直接换 **SSH over 443** —— 这是个绕过干扰的稳定通道。

## 六、接入两级流水线（已完成）

修改 `src/organizer.py`，把检测与分类串成两级：

```
照片 → 【第一级】YOLO 物体检测
            ├── 检测到物体 → 按物体归类（人像 / 宠物动物 / 美食餐具……）
            └── 没检测到   → 【第二级】分类模型判断整图类型（截图/文档/风景/表情包）
```

同时加了 `--no-cls` 参数用于 A/B 对照，以及"判定来源"统计（多少张来自检测、多少张来自兜底）。

### A/B 对照实验结果（52 张个人相册）

| | 只用检测（旧） | 检测 + 分类兜底（新） |
|---|---|---|
| YOLO 检测判定 | 38 张 | 38 张 |
| 分类兜底判定 | 0 张 | **14 张** |
| **未识别** | **14 张（26.9%）** | **0 张（0%）** |

那 14 张照片的分类结果：风景 9 张、美食餐具 3 张、文档 1 张、表情包 1 张。

### 这次升级完整走完了一个工程闭环

```
发现问题（26.9% 未识别）
   → 分析原因（任务类型不匹配：截图/文档里没有"物体"可检测，是任务选错了，不是模型不够强）
   → 采集标注 1027 张数据（分类任务零框选成本）
   → 训练分类模型（独立验证集 94.6%）
   → 接入兜底
   → 量化验证（未识别率 26.9% → 0%）
```

**这次经历印证了一个判断**：指标不好时，先怀疑**任务定义和数据**，再怀疑模型。
如果一开始就想着"换个更大的检测模型"，26.9% 这个数字是治不好的 —— 因为那些图里本来就没有物体。
